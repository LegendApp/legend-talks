# AI Chat History {shared=rnconnection-title shared-resize=preserve class="text-center font-semibold tracking-tight text-7xl"}

<ChatArchitecture />

<!--
1. Before we get into the numbers, let me show you how the React Native version works.

Here's where the work actually happens.

First we find the chat files. That's native. The C++ catalog discovers the conversations on disk.

2. Then we parse the metadata. Titles, providers, dates. Enough to show the list of chats without opening every conversation in full.

3. When I select a chat, the C++ parser opens it and builds the transcript rows and markdown blocks. I expose that through Nitro Modules.

This is a custom parser for this workload. I'm not saying every desktop app needs you to write a C++ parser.

4. Now React comes in. LegendList virtualizes the conversation.

The data source gives it row indices and fetches metadata as needed. I don't need a giant JavaScript array containing every message's markdown.

5. For each visible markdown row, Enriched Markdown gets a native block ID. The content stays native for the markdown renderer. React still composes the row, including images and controls.

So React doesn't have to do every piece of work. It coordinates the pieces that are good at that work.

6. And React is where I build the app UI. The layout, the state, what happens when I select another chat.

7. The composer is a React component too. It coordinates input and the native controls underneath it.

8. And settings belong on that React side as well. These last three are UI responsibilities, not extra sequential stages that all run after a message renders.

That's the split I want. Native code for the work that benefits from it. React for composing and coordinating the app.

No WebView is required for this core UI. This is regular React Native, with native modules and native views.

So what does that look like in the measurements?

Settings is an architectural responsibility here, not a measured startup phase.

<!--

iOS. Android. macOS. Windows. Web.

Full dots are supported application targets. Half-filled Web dots mean the web UI can be reused, but platform APIs need adaptation. That's why Tauri, Electron and Deno have a partial Web dot.
